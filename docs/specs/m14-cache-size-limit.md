# Спека: у кеша появляется верхняя граница объёма

**Репозиторий:** `google-keyword-ai-mcp` · **Веха:** `1 из 1` · **Дата:** `2026-09-04` · **Исполнитель:** Codex

## Контекст

Предыдущая веха M13 (`docs/specs/m13-cache-retention.md`, влита в `0db0f82`)
научила кеш выметать ПРОСРОЧЕННОЕ и дала команды `gkai cache status` и
`gkai cache purge`. Она сознательно НЕ ограничивала объём: пока записи живы по
TTL, кеш растёт без потолка. У Google Ads TTL идей — 7 дней, исторических
метрик — 30 дней; у Search Console одна запись может нести до 25 000 строк
ответа. Мёртвого в такой базе нет, а места она занимает сколько угодно.

Эта веха вводит потолок и вытеснение самых давно читанных записей (LRU).
Читай код M13 и опирайся на существующие типы (`SqliteCache`, `CacheCounts`,
`CacheStatusData`), ничего в них не переписывая без нужды.

Веха ТАКЖЕ закрывает дыру в тестах M13 — см. п. 6 «Что делать». Дыра лежит
ровно в том методе `set()`, который эта веха меняет, поэтому чинится здесь, а
не отдельным прогоном.

## Проверенные факты

Проверено вживую 2026-09-04 на этом репозитории, до написания спеки. Чего
здесь нет — считать неизвестным и НЕ реализовывать.

1. **Цена LRU измерена и она мала.** На базе из 5000 записей по 2,5 КБ: 2000
   чтений без записи — 33 мс (0,017 мс на чтение); те же 2000 чтений с
   `UPDATE` на каждое — 69 мс (0,035 мс). Замедление в 2,1 раза, но в
   абсолюте это +18 микросекунд на попадание в кеш против сетевого вызова в
   10–1000 мс. Поэтому обновление отметки чтения на КАЖДОМ попадании
   допустимо, и городить прореживание («обновлять не чаще раза в час») не
   надо: это усложнение без выигрыша.
2. **Проверка объёма СТОИТ ДОРОГО, и это определяет устройство вехи.** На базе
   в 50 000 записей (119 МиБ payload) `SELECT sum(length(payload)) FROM
   cache_entries` занимает **62,7 мс**, тогда как `SELECT count(*)` — около
   нуля (SQLite берёт его по индексу). Отсюда прямое следствие: считать сумму
   на КАЖДОЙ записи нельзя — один `gkai expand` делает сотни `set()`, это
   добавило бы порядка 19 секунд чистых накладных расходов. Устройство
   вытеснения в п. 5 продиктовано этим замером, а не вкусом.
3. **`NULL` в `last_read_at` сортируется ПЕРВЫМ** при `ORDER BY ... ASC`
   (проверено: `['nul', 'a', 'b']`). Поэтому запись с неизвестной отметкой
   чтения естественно вытесняется раньше всех, и отдельного правила для неё
   не нужно.
4. **Размер типичной записи.** Живой прогон `gkai research` + два `gkai
   expand`: 46 записей, `payload_bytes` = 114 200, то есть в среднем 2483
   байта на запись autocomplete. Записи Search Console и Google Ads
   значительно крупнее — именно они и упираются в потолок.
5. **Схема и порядок миграций.** `SCHEMA_VERSION = 3`, список `MIGRATIONS` в
   `src/google_keyword_ai/storage/migrations.py`. Образец добавления колонки —
   `_migration_3`: `ALTER TABLE runs ADD COLUMN ...`, существующие строки
   читаются как `NULL`. Каждая миграция идёт в своей транзакции `BEGIN
   IMMEDIATE` с перечитыванием `PRAGMA user_version` внутри неё.
6. **Правило репозитория для миграций** (`AGENTS.md`, раздел «Изменение схемы
   БД»): поднимаешь версию — пиши тест, который проверяет апгрейд со СТАРОЙ
   версии С ДАННЫМИ, а не создание пустой базы с нуля.
7. **Что уже есть после M13:** `SqliteCache.purge_expired()`, `purge_all()`,
   `counts() -> CacheCounts(entries, expired_entries, payload_bytes)`, флаг
   экземпляра `_sweep_attempted`, настройки `cache_enabled` и
   `cache_sweep_enabled`, удаление парой `WHERE key = ? AND expires_at IS ?`,
   `_has_expired(expires_at, now)` с одним `now` на просмотр.
8. **Дыра в тестах M13, подтверждённая мутациями** (каждая мутация пережила
   весь набор — тесты остались зелёными):
   - убрать проверку `cache_sweep_enabled` из условия в `set()` — 30 тестов
     зелены;
   - перенести подметалку ДО проверки `cache_enabled` — 16 тестов зелены;
   - убрать `logger.warning` из ветки best-effort — 16 тестов зелены.
   Код при этом правильный; отсутствуют именно проверки.

9. **Сама миграция №4 проверена вживую до написания спеки.** На настоящей базе
   версии 3 С ДАННЫМИ три оператора (`ALTER TABLE ADD COLUMN`, `UPDATE ... SET
   last_read_at = created_at`, `CREATE INDEX`) прошли в ОДНОЙ транзакции:
   `user_version` стал 4, у всех строк `last_read_at` равен `created_at`,
   длины payload не изменились.
10. **Индексом это пользуется, а вариантом с COALESCE — нет.** `EXPLAIN QUERY
   PLAN` для `ORDER BY last_read_at ASC` даёт `SCAN cache_entries USING INDEX
   ix_cache_entries_last_read_at`; для `ORDER BY COALESCE(last_read_at,
   created_at)` — `SCAN cache_entries` плюс `USE TEMP B-TREE FOR ORDER BY`.
   Это и есть причина, по которой backfill обязателен, а не косметика.

### 1. Миграция №4: отметка последнего чтения

Поднять `SCHEMA_VERSION` до 4 и добавить `_migration_4` в список `MIGRATIONS`:

```sql
ALTER TABLE cache_entries ADD COLUMN last_read_at TEXT;
UPDATE cache_entries SET last_read_at = created_at;
CREATE INDEX ix_cache_entries_last_read_at ON cache_entries (last_read_at);
```

**Заполнение существующих строк обязательно и не является косметикой.** Если
оставить `NULL`, порядок вытеснения пришлось бы считать через
`COALESCE(last_read_at, created_at)`, и тогда индекс по колонке не
использовался бы при сортировке. С заполнением сортировка — простое
`ORDER BY last_read_at`, и индекс работает.

Колонка остаётся nullable, и утверждать «`NULL` тут не появится никогда»
НЕЛЬЗЯ: строку можно вставить и напрямую SQL-ом, что тесты и делают. Правило
такое: САМ КОД никогда не пишет в неё `NULL` (п. 2), а строка с `NULL`
считается прочитанной раньше всех и вытесняется первой — это происходит само
собой, потому что `NULL` сортируется первым при `ASC` (факт 3), и отдельной
ветки под него писать не надо.

Больше миграций не добавлять, прежние не трогать.

### 2. `set()` пишет отметку чтения

В `INSERT ... ON CONFLICT` добавить колонку `last_read_at` со значением, равным
`created_at` (той же меткой, что уже вычисляется), и обновлять её в ветке
`DO UPDATE`. Свежезаписанная запись считается только что прочитанной.

### 3. `get()` обновляет отметку при попадании

При попадании (запись найдена и НЕ просрочена) выполнить
`UPDATE cache_entries SET last_read_at = ? WHERE key = ?` с текущим моментом,
после чего вернуть payload. При промахе и при просроченной записи отметку не
обновлять — просроченную мы и так удаляем.

Чтение payload и обновление отметки идут РАЗНЫМИ операторами, и между ними
конкурирующее вытеснение может успеть удалить эту запись по прежней паре. Тогда
`get()` вернёт payload уже удалённой записи. Это допустимо и специально
разрешено: значение было валидным в момент чтения, а следующий запрос просто
сходит к провайдеру. Городить общую транзакцию ради этого не надо.

Обновление отметки — best-effort в том же смысле, что и подметалка: если
`UPDATE` поднял `SQLAlchemyError`, `get()` обязан ВЕРНУТЬ найденный payload и
залогировать ошибку, а не превратить попадание в промах и не выпустить
исключение наружу. Кеш, который не смог записать статистику, всё ещё кеш.

### 4. Настройка потолка

В `Settings` добавить `cache_max_bytes: int = 536870912` (512 МиБ) рядом с
`cache_sweep_enabled`. Значение `0` означает «без ограничения». Отрицательное
значение — `InvalidConfigurationError` через валидатор, по образцу соседних
валидаторов в `config.py`.

Потолок сравнивается с суммой длин `payload` (то есть с `payload_bytes` из
`counts()`), а НЕ с размером файла базы: в файле лежит ещё и история прогонов,
которую эта веха не трогает. Сказать это в докстринге и в `cli.md`.

**Запас (slack), при котором пересчитывается объём:** `max(1, cache_max_bytes
// 100)` байт. Это не отдельная настройка, а выражение — считать его прямо в
коде. Смысл в факте 2: пересчёт суммы стоит десятки миллисекунд, поэтому он
делается не на каждой записи, а раз в «один процент потолка» записанных байт.
Накладные расходы держатся около 1 %, и они не зависят от размера кеша.

### 5. Вытеснение по давности чтения

Новый метод `SqliteCache.evict_over_limit(self) -> int`: удаляет самые давно
читанные записи, пока сумма длин `payload` не станет меньше либо равна
`cache_max_bytes`; возвращает число удалённых.

Порядок:

1. Если `cache_max_bytes` равен 0 — вернуть 0, ничего не читая.
2. `SELECT key, last_read_at, length(payload) FROM cache_entries ORDER BY
   last_read_at ASC` — payload не поднимать.
3. Идти по списку от самых давних, набирая записи на удаление, пока СУММА
   ОСТАВШИХСЯ не уложится в потолок.
4. Удалять пачками не больше 500 ключей, оператором
   `DELETE FROM cache_entries WHERE key = ? AND last_read_at IS ?` со
   значением `last_read_at`, увиденным при просмотре.

**Проход РОВНО ОДИН, цикла «пока не уложились» быть не должно.** Причина в
том, что условие «уложились» не всегда достижимо: одна запись может сама по
себе быть больше потолка, а парное удаление может снять ноль строк, если её в
этот момент прочитали. Метод делает один проход по снимку и возвращает
управление, даже если сумма осталась выше потолка. Цикл здесь означал бы
зависание на первом же таком случае.

**Удаление парой обязательно по той же причине, что и в M13:** между просмотром
и удалением другой процесс может ПРОЧИТАТЬ запись, и её `last_read_at`
изменится. Такую запись вытеснять уже нельзя — она только что оказалась
нужной, — и сравнение с прочитанным значением само её пропускает.

**Гарантия формулируется честно и только для одного процесса:** после
возврата из `set()` сумма длин `payload`, записанных ЭТИМ процессом, не
превышает `cache_max_bytes + slack`. Утверждать «сумма всегда не больше
`cache_max_bytes`» НЕЛЬЗЯ по трём причинам: между пересчётами дописывается до
`slack` байт; параллельный процесс пишет свои; одна запись может быть больше
потолка. Тест на гарантию — однопроцессный.

### 5а. Когда вытеснение запускается

Здесь исправлена ошибка, которую нашли оба ревьюера в первой редакции этой
спеки. Привязывать вытеснение к «единственной попытке на экземпляр» НЕЛЬЗЯ:
один `SqliteCache` обслуживает сотни `set()` подряд (`gkai expand`), и после
первой же записи потолок перестал бы действовать до конца сценария — то есть
веха не делала бы ровно того, ради чего заводится.

Правило такое:

1. У экземпляра есть счётчик `_bytes_since_eviction`, начинается с нуля.
2. При ПЕРВОМ `set()` экземпляра, как и в M13, один раз выполняется
   `purge_expired()`, а сразу за ним — `evict_over_limit()`. Так подхватывается
   кеш, который прошлые запуски оставили выше потолка. Счётчик обнуляется.
3. КАЖДЫЙ `set()` после успешной вставки прибавляет к счётчику длину
   записанного `payload`.
4. Как только счётчик достигает `slack` (выражение задано в п. 4), выполняется
   `evict_over_limit()`, и счётчик обнуляется.

Порядок внутри первого вызова важен: сначала выметается просроченное, и только
потом, если места всё ещё не хватает, вытесняется живое. Вытеснять то, что и
так помрёт по TTL, — значит выбрасывать полезные записи вместо мусора.

Вытеснение, как и подметалка, не выполняется при `cache_enabled=False`.
**Настройка `cache_sweep_enabled` управляет ОБОИМИ видами автоматического
обслуживания — и выметанием просроченного, и вытеснением по объёму.** Это
сказано явно, потому что иначе буквалист вправе решить иначе; отдельного
выключателя под LRU не заводить. Написать это в докстринге настройки и в
`cli.md`.

Вытеснение best-effort: `SQLAlchemyError` логируется, `set()` всё равно
записывает своё значение и не поднимает исключение наружу.

## Критерии приёмки

Окружение готовит принимающий ДО запуска: интерпретатор и зависимости лежат в
клоне, команды запускаются как `.venv/bin/python -m ...` из корня клона. Сети
нет, Docker недоступен — команд установки и `docker` в критериях быть не должно.

**У каждого критерия РОВНО ОДНО утверждение и ровно один тест.** Связка через
`-k "a or b"` запрещена: она даёт зелёный, когда совпала часть, и пропускает
отсутствующий тест. Это не стилистика — ровно так в предыдущей вехе прошёл
ложный критерий (см. `TASKS.md`).

**AC-012 агрегирующий; при его провале остальные критерии всё равно выполнить
и отчитаться по каждому.**

- **AC-001.** База версии 3 С ДАННЫМИ поднимается до версии 4: колонка
  `last_read_at` появляется, у КАЖДОЙ существующей строки она равна её
  `created_at`, длины payload не изменились.
  Проверка: `.venv/bin/python -m pytest -q tests/test_migrations.py -k last_read_at_backfill`
- **AC-002.** `set()` записывает `last_read_at`, равный `created_at`, и при
  повторной записи того же ключа обновляет обе метки.
  Проверка: `.venv/bin/python -m pytest -q tests/test_cache.py -k set_stamps_last_read_at`
- **AC-003.** `get()` при попадании двигает `last_read_at` вперёд.
  Проверка: `.venv/bin/python -m pytest -q tests/test_cache.py -k get_touches_last_read_at`
- **AC-004.** Отказ `UPDATE` отметки в `get()` не превращает попадание в
  промах: payload возвращён, исключение наружу не ушло.
  Проверка: `.venv/bin/python -m pytest -q tests/test_cache.py -k touch_failure_still_returns_payload`
- **AC-005.** `evict_over_limit()` удаляет ИМЕННО самые давно читанные: на
  наборе из пяти записей при потолке, допускающем ровно две, в базе остаются
  те две, у которых `last_read_at` самый свежий. Проверяется сравнением
  МНОЖЕСТВА ОСТАВШИХСЯ КЛЮЧЕЙ с ожидаемым, а не их количеством.
  Проверка: `.venv/bin/python -m pytest -q tests/test_cache.py -k evicts_least_recently_read`
- **AC-006.** Вытеснение удаляет парой `(key, last_read_at)`: запись,
  прочитанная между просмотром и удалением, остаётся в базе.
  Проверка: `.venv/bin/python -m pytest -q tests/test_cache.py -k touched_entry_survives_eviction`
- **AC-007.** ГЛАВНЫЙ КРИТЕРИЙ ВЕХИ. Последовательность настоящих вызовов
  `set()` на ОДНОМ экземпляре `SqliteCache`, суммарно записывающая заведомо
  больше потолка (не меньше десятикратного), оставляет `payload_bytes` не выше
  `cache_max_bytes + max(1, cache_max_bytes // 100)`. Реализация, вытесняющая
  только один раз на экземпляр, этот критерий НЕ проходит.
  Проверка: `.venv/bin/python -m pytest -q tests/test_cache.py -k many_writes_stay_under_limit`
- **AC-008.** `cache_max_bytes=0` — вытеснения нет, сколько бы записей ни
  лежало.
  Проверка: `.venv/bin/python -m pytest -q tests/test_cache.py -k eviction_disabled_by_zero`
- **AC-009.** При `cache_sweep_enabled=False` не выполняется НИ подметалка, НИ
  вытеснение: и просроченная запись, положенная ДО первого `set()`, и записи
  сверх потолка переживают серию `set()`.
  Проверка: `.venv/bin/python -m pytest -q tests/test_cache.py -k sweep_switch_disables_both`
- **AC-010.** При `cache_enabled=False` просроченная запись, положенная ДО
  первого `set()`, переживает `set()`, и новая запись не появляется.
  Проверка: `.venv/bin/python -m pytest -q tests/test_cache.py -k cache_disabled_keeps_expired`
- **AC-011.** `gkai cache status` печатает `max_bytes`, равный настройке:
  тест читает ЗНАЧЕНИЕ поля из конверта, а не только факт его наличия.
  Проверка: `.venv/bin/python -m pytest -q tests/test_cache_commands.py -k status_reports_max_bytes`
- **AC-012.** Полный набор проверок зелёный (агрегирующий критерий).
  Проверка:

## Контракт на невыполнимое

> Если два требования противоречат друг другу, два пина несовместимы или
> требование невыполнимо в этом окружении — **ОСТАНОВИСЬ и доложи** в поле
> `blocked_reason` финального отчёта, приложив доказательство (вывод команды,
> текст ошибки резолвера). Обходить объявленную несовместимость запрещено:
> `--no-deps`, `--force-reinstall`, вендоринг, подмена тулчейна, отключение
> проверок, игнор constraints — всё это считается провалом задачи, а не
> решением. Остановка с внятной причиной — правильный исход, а не поражение.
>
> Если одна и та же команда упала дважды с той же ошибкой — не запускай её в
> третий раз, не изменив подхода. Если подхода нет — остановись и доложи.
