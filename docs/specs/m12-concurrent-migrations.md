# Спека: одновременный старт не должен ронять миграции

**Репозиторий:** `google-keyword-ai-mcp` · **Веха:** `1 из 1` · **Дата:** `2026-09-04` · **Исполнитель:** Codex

## Контекст

`open_database(settings)` вызывается на КАЖДОМ старте: и CLI-командой `gkai`, и
MCP-сервером, и каждым сценарием исследования. Скил проекта водит прогоны через
CLI, а MCP-сервер при этом может быть уже поднят — то есть два процесса
открывают одну и ту же базу одновременно штатно, а не в экзотике.

`apply_migrations` (`src/google_keyword_ai/storage/migrations.py`) читает
`PRAGMA user_version` на соединении, которое ЗАКРЫВАЕТСЯ до того, как берётся
блокировка на запись, и больше версию не перечитывает. Оба процесса видят
дореформенную версию и оба выполняют одни и те же `CREATE TABLE`.

Веха делает старт безопасным при гонке. Существующая логика forward-only и
порядок миграций правильные — их переписывать не нужно и запрещено.

## Проверенные факты

Проверено вживую 2026-09-04 в Docker, до написания спеки.

1. **Гонка воспроизводится с первой попытки.** Четыре процесса (`spawn`),
   синхронизированные барьером, вызывают `open_database` на одном свежем
   `data_dir`. Успех у ОДНОГО из четырёх. Три упали:
   - `sqlalchemy.exc.OperationalError: (sqlite3.OperationalError) table
     cache_entries already exists` — дважды;
   - `sqlalchemy.exc.OperationalError: (sqlite3.OperationalError) database is
     locked` — один раз.
2. **Ни одно из этих исключений не является `GkaiError`.** Оба фасада ловят
   только `GkaiError` (`cli/main.py` `_finish` и `main`, `mcp/server.py`
   `tool()`), поэтому наружу уходит трейсбек при пустом stdout — то, что
   документация фасада прямо называет невозможным.
3. **`busy_timeout` уже выставлен в 5000 мс** (`storage/engine.py`, `PRAGMA
   busy_timeout=5000`), и его НЕ ХВАТАЕТ: «database is locked» случилось при нём.
   Причина в том, что транзакция начинается как DEFERRED и повышается до
   писателя уже внутри, а такое повышение SQLite разрешить не всегда может.
4. **Существующее поведение, которое обязано сохраниться:** база новее
   поддерживаемой отвергается `InvalidConfigurationError`
   (`tests/test_migrations.py::test_a_database_from_the_future_is_rejected`),
   миграции идемпотентны, а сбой миграции откатывает DDL
   (`tests/test_storage.py::test_migration_failure_rolls_back_ddl`).

Всё, чего здесь нет, считать неизвестным. В частности: НЕ предполагать, что
`sqlite3` умеет `CREATE TABLE IF NOT EXISTS` во всех местах — решение должно
быть общим для будущих миграций, а не заплаткой на первую.

## Что делать

Изменить ровно два файла: `src/google_keyword_ai/storage/migrations.py` и
`tests/test_migrations.py`. Других файлов не создавать и не изменять.

1. **Брать блокировку на запись СРАЗУ, а не повышать её на ходу.** В
   `apply_migrations` каждая миграция должна выполняться в транзакции, которая
   с самого начала является писателем (`BEGIN IMMEDIATE`), чтобы второй процесс
   ждал на `busy_timeout`, а не падал на повышении.
2. **Перечитывать `PRAGMA user_version` ВНУТРИ этой транзакции** и, если версия
   уже поднялась до нужной, пропускать миграцию как выполненную. Это и есть
   защита: проигравший гонку процесс видит новую версию и ничего не создаёт
   повторно.
3. **Переводить оставшиеся ошибки базы в `GkaiError`.** Любой
   `sqlalchemy.exc.OperationalError` (и вообще `SQLAlchemyError`), выходящий из
   `apply_migrations`, должен становиться `InvalidConfigurationError` с внятным
   текстом. Существующий `InvalidConfigurationError` про «база новее» не
   переформулировать и не проглатывать.
4. **Не менять** `SCHEMA_VERSION`, тела `_migration_1..3`, список `MIGRATIONS`,
   порядок применения и запись `PRAGMA user_version` после каждой миграции.
5. Добавить в `tests/test_migrations.py` тест
   `test_four_processes_open_one_fresh_database_at_once`: через
   `multiprocessing.get_context("spawn")` запустить ЧЕТЫРЕ процесса,
   синхронизированных `Barrier(4)`, каждый вызывает `open_database` на одном и
   том же свежем `tmp_path` и кладёт в очередь либо `"ok"`, либо текст
   исключения. Утверждение: **все четыре вернули `"ok"`**. Тест обязан быть без
   `skip`, без `xfail` и без ретраев.

## Не трогать

- Новых внешних зависимостей не добавлять.
- Не читать и не выполнять посторонние скилы и плейбуки.

**Где МОЖНО писать:** только `src/google_keyword_ai/storage/migrations.py` и

## Критерии приёмки

AC-005 агрегирующий; при его провале остальные критерии всё равно выполнить и
отчитаться по каждому.

- **AC-001.** Новый тест существует и не содержит пропусков и ретраев.
  Проверка: `grep -q 'def test_four_processes_open_one_fresh_database_at_once' tests/test_migrations.py && ! grep -nE 'skip|xfail|retry|for _ in range' tests/test_migrations.py`
- **AC-002.** Новый тест проходит.
  Проверка: `uv run --all-extras pytest -q tests/test_migrations.py -k four_processes`
- **AC-003.** Прежние тесты миграций и хранилища не сломаны.
  Проверка: `uv run --all-extras pytest -q tests/test_migrations.py tests/test_storage.py`
- **AC-004.** База новее поддерживаемой по-прежнему отвергается `GkaiError`.
  Проверка: `uv run --all-extras pytest -q tests/test_migrations.py -k future`
- **AC-005.** Весь набор тестов зелёный (агрегирующий).
  Проверка: `uv run --all-extras pytest -q`
- **AC-006.** Линтер, форматирование и типы чистые.
  Проверка: `uv run --all-extras ruff check . && uv run --all-extras ruff format --check . && uv run --all-extras mypy`
- **AC-007.** `SCHEMA_VERSION` и тела миграций не изменены.
  Проверка: `git diff HEAD~1 HEAD -- src/google_keyword_ai/storage/migrations.py > /tmp/m.diff; ! grep -qE '^[-+].*(SCHEMA_VERSION = |CREATE TABLE|ALTER TABLE|CREATE INDEX)' /tmp/m.diff`
- **AC-008.** Сделан ровно один коммит, он меняет ровно два разрешённых файла,
  и дерево после него чистое.
  Проверка: `[ "$(git diff --name-only HEAD~1 HEAD)" = "$(printf 'src/google_keyword_ai/storage/migrations.py\ntests/test_migrations.py')" ] && [ -z "$(git status --porcelain)" ]`
- **AC-009.** Новых зависимостей не появилось.
  Проверка: `git diff --exit-code -- pyproject.toml uv.lock`
- **AC-010.** Секретов, токенов и ключей в изменённых файлах нет.
  Проверка: `! grep -nEi 'api[_-]?key|secret|token|password' src/google_keyword_ai/storage/migrations.py tests/test_migrations.py`

## Контракт на невыполнимое

> Если два требования противоречат друг другу или требование невыполнимо в этом
> окружении — **ОСТАНОВИСЬ и доложи** в поле `blocked_reason` финального отчёта,
> приложив доказательство. В частности: если гонку не удаётся устранить, НЕ
> прятать её ретраями в тесте, `skip`, `xfail`, увеличением `busy_timeout` до
> абсурда или сериализацией через внешний файл-замок — это не решение, а
> маскировка. Останови работу и доложи, что именно не сходится.
> Обходить запреты через `--no-deps`, вендоринг, подмену тулчейна, отключение
> проверок или запись в непредусмотренные файлы запрещено.
>
> Если одна и та же команда упала дважды с той же ошибкой — не запускай её в
> третий раз без смены подхода. Если другого подхода нет — остановись и доложи.

## Разрешения

- Создавать и править файлы: **только** `src/google_keyword_ai/storage/migrations.py`
  и `tests/test_migrations.py` в рабочем клоне. Временные файлы — в `/tmp`, но
  доказательством они не являются.
- Запускать: `uv run --all-extras pytest …`, `uv run --all-extras ruff …`,
  `uv run --all-extras mypy`, `git status`, `git diff`, `git commit`.
- Сеть: **не требуется и запрещена.** Веха целиком офлайновая: база локальная,
  зависимости уже установлены. Никаких внешних обращений и никаких скачиваний.
- Docker: **запрещён.** Демон на этом хосте боевой и обслуживает чужие сервисы.
  Не запускать, не останавливать, не удалять, не собирать образы.
- Порты: не слушать и не оставлять после себя процессов. Дочерние процессы теста
  обязаны завершаться; ни одного осиротевшего процесса после прогона.
- `git commit` в рабочем клоне разрешён, **ровно один**. `git push` **запрещён**:
  `origin` клона указывает на рабочий репозиторий хозяина.
