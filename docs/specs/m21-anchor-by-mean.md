# M21 — якорь по измеренному среднему и верхний ключ в competitor/site

Веха чинит одно наблюдаемое искажение выдачи: относительный спрос может
показывать значения вроде **3268** вместо доли от 100, а в сценариях
`competitor` и `site` самый важный ключ вообще остаётся без значения.

Обе правки лежат на ОДНОМ механизме — отборе кандидатов и выборе якоря
(`select_research_candidates` + `_enrich_demand`), поэтому это одна веха.

Клон `/home/deploy/exec-clones/gkai-m21-anchor`, ветка `m21-anchor-by-mean`,
базовый коммит — текущий `main`. Окружение готово: `.venv` с Python 3.14,

Спека приезжает в клон untracked — включи её в свой коммит.

## Почему так, а не иначе (замеры, а не рассуждения)

Живой `gkai demand` (ru/RU, `today 12-m`), один пакет из пяти ключей:

| ключ | relative_demand | измеренных недель |
|---|---|---|
| купить квартиру москва | 100.0 | 52/52 |
| купить квартиру мытищи | 5.09 | 49/52 |
| купить квартиру балашиха | 4.49 | 37/52 |
| купить квартиру химки | 3.86 | 37/52 |
| купить квартиру щелково | 3.06 | 13/52 |

1. **Причина завышения — деление на маленькое среднее.** Возьми якорем нижний
   ключ («щелково»), и «москва» получит `100 / 3.06 ≈ 3268` — ровно то число,
   что видели в прогоне M20. Возьми верхний — хвост остаётся читаемым (3.06).
2. **Низкое покрытие — спутник, а не причина.** Ключ может иметь 52/52 недель и
   среднее около нуля; завышение будет тем же. Поэтому критерий отбора —
   наибольшее **измеренное среднее**, а не наибольшее покрытие.
3. **Выбрать якорь ДО запроса невозможно:** среднее известно только из ответа
   Google. Отсюда два прохода.
4. **Второй проход бесплатен.** Первый пакет уже возвращает средние всех своих
   участников, и `measured_mean(result, keyword)` даёт их для любого из них.
   Пересчёт долей относительно другого участника ТОГО ЖЕ пакета — чистая
   арифметика над уже полученным ответом. Число обращений к Trends не меняется.
5. **Верхний ключ competitor/site пропадает.** Проверено зондом на наборе, где
   верхний ключ назван не «seed»: в обоих сценариях он выходит с
   `demand_relative=None`, `demand_status=None`, то есть печатается как «не
   ранжирован». Причина: `demand_seed=notable` (максимум по Ads) и
   `demand_seed=frequent` (максимум по показам GSC) уезжают в
   `select_research_candidates` как СИД и исключаются из кандидатов. В нише
   исключение сида оправдано — сид там запрос пользователя, а не результат;
   в competitor/site исключаемый ключ сам и есть главный результат.

> **Граница применимости.** Разброс 33:1 измерен на ОДНОМ живом наборе из пяти
> ключей. Это не доказательство «верно при любом разбросе»: при разбросе в
> тысячи раз хвост может дать честный `0.0` со статусом `measured`. Спека
> требует тест на такой разброс (AC-005) — чтобы поведение было ЗАФИКСИРОВАНО
> наблюдением, а не предположено. Если наблюдаемое поведение окажется иным, чем
> ожидает критерий, это контракт на невыполнимое: доложи, не подгоняй.

## Что сделать

### 1. Чистый выбор якоря (`src/google_keyword_ai/demand.py`)

Добавить чистую функцию, выбирающую якорь по УЖЕ полученному результату:
среди переданных ключей взять тот, у кого наибольшее `measured_mean`. Ключи без
измеренных недель (`measured_mean is None`) и с нулевым средним кандидатами в
якорь не являются. При равенстве средних — берётся первый по порядку
переданного списка (устойчиво, без зависимости от порядка в ответе Google).
Если годного ключа нет — функция возвращает `None`, и вызывающий оставляет
прежний якорь; поведение `anchor_collapsed` не меняется.

Слой чистый: сети и провайдеров здесь нет, функция принимает `TrendsResult`.

### 2. Два прохода (`src/google_keyword_ai/pipeline/scenarios.py`)

`_enrich_demand`: первый пакет запрашивается как сейчас (состав вслепую), но
после ответа якорь выбирается функцией из пункта 1 среди участников ЭТОГО
пакета. Дальше:

- список `keywords` первого пакета переупорядочивается так, чтобы выбранный
  якорь стоял первым (`_batch_rows` берёт якорь как `batch.keywords[0]`, а
  средние ищет по ИМЕНИ, поэтому переупорядочивания достаточно и трогать
  `combine` не нужно);
- остальные пакеты собираются с выбранным якорем;
- `stats.anchor` сообщает выбранный якорь, а не первого кандидата.

**Число обращений к Trends обязано остаться прежним.** Участник, ранее бывший
якорем, уже ранжирован в первом пакете и в остальные не добавляется.

### 3. Верхний ключ в competitor/site (`scenarios.py`)

`notable` и `frequent` остаются subject одиночного Trends (`_fetch_trends`) —
это отдельная задача, её не трогать. Но в отбор кандидатов спроса они как сид
уезжать не должны: в этих двух сценариях сида нет, исключать нечего.
В `niche` исключение сида сохраняется без изменений.

### 4. Документация

`docs/demand.md`: заменить утверждение о том, что якорем становится верх
отсортированных кандидатов. Описать два прохода, критерий выбора и то, что
явный `--demand-anchor` по-прежнему главнее автоматического выбора.

## Что проверено вживую, а что предположение

Каждое утверждение спеки о существующем коде подтверждено чтением тела, а не
памятью. Проверял на текущем `main`:

| Утверждение | Чем подтверждено |
|---|---|
| `_batch_rows` берёт якорь как `batch.keywords[0]` | `demand.py:123`, `anchor = batch.keywords[0]` |
| средние ищутся по ИМЕНИ, а не по позиции | `_measured_values` → `result.keywords.index(keyword)`; отсюда достаточно переупорядочить план |
| `measured_mean(result, keyword) -> float \| None` | `demand.py:110`, возвращает `fmean(values) if values else None` |
| `combine` не сверяет якоря разных пакетов между собой | тело `combine`: только `enumerate(batches)` и `_batch_rows`, никакой проверки идентичности |
| `demand_seed` доезжает до отбора кандидатов как сид | `_research_data` зовёт `_enrich_demand(context, keywords, demand_seed, used)`; параметр там называется `seed` и уходит в `select_research_candidates(names, seed, …)` |
| якорь сейчас — первый кандидат | `select_research_candidates`: `selected_anchor = candidates[0] if anchor is None else anchor` |
| `notable` = максимум по `avg_monthly_searches` | тело `CompetitorResearch.run`, `max(keywords, key=… avg_monthly_searches or 0)` |
| `frequent` = максимум по `gsc_impressions` | тело `ExistingSiteResearch.run` |
| при бюджете по умолчанию 3 вызова Trends | `Budget.max_trends_calls = 3`, тест `test_all_scenarios_share_optional_demand` требует `len(trends.calls) == 3` |
| база 669 тестов | прогон в Docker на 3.14 и 3.12 перед началом вехи |

**Предположение, НЕ проверенное:** что переупорядочивания списка `keywords`
первого пакета достаточно и `combine`/`_batch_rows` править не придётся. Оно
следует из двух проверенных фактов выше (якорь берётся позиционно из плана,
средние ищутся по имени), но целиком вживую не прогонялось. Если окажется
неверным — это контракт на невыполнимое, доложи.

## Контракт на невыполнимое

Остановись и доложи `blocked` с точной причиной, если: переупорядочивания
первого пакета не хватает и требуется правка `combine`/`_batch_rows`; число
обращений к Trends нельзя сохранить прежним; наблюдаемое поведение на разбросе
в тысячу раз не удаётся зафиксировать тестом. Обходить несовместимость, глушить
код возврата, помечать тест `skip`/`xfail`, ослаблять ассерты — запрещено.

## Контракт отчёта

Положи в корень клона `report.json`:

```json
{"criteria": [
  {"id": "AC-001", "status": "pass", "command": "<команда-доказательство>",
   "rc": 0, "note": "коротко, что получилось"}
]}
```

Статусы: `pass` / `fail` / `blocked`. По одной записи на каждый критерий
AC-001…AC-008, ни одного лишнего. `command` — та команда, которой критерий
реально доказан, целиком, без `|| true` и без подмены окружения.
